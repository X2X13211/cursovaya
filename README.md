## 2. Атрибуты качества и выбранный архитектурный стиль

### Измеримые атрибуты качества

| Атрибут качества | Измеримая формулировка |
|---|---|
| **Защита персональных данных ** | Паспортные данные, телефоны и адреса жильцов хранятся в зашифрованном виде (AES-256 / pgcrypto). Доступ ограничен ролевой моделью RBAC: комендант видит жильцов только своего корпуса, студент — только свой профиль. Персональные данные не попадают в системные логи (маскирование) |
| **Надёжность транзакций (Anti-Overbooking)** | Процедура распределения места и заключения договора найма выполняется в единой ACID-транзакции с пессимистической блокировкой (`SELECT ... FOR UPDATE`). Ситуация двойного заселения на одно койко-место исключена на 100% при параллельных запросах |
| **Производительность автопоиска** | Алгоритм автоматического подбора свободных мест с фильтрацией по полу, курсу, факультету и корпусу 

### Выбранный архитектурный стиль — Модульный монолит

Для проекта выбран **модульный монолит**. 

Обоснование:

| Критерий | Микросервисы | Модульный монолит (выбор) |
|---|---|---|
| Сложность для команды 1 чел. | Высокая | Низкая |
| Распределённые транзакции | Требуют Saga / 2PC | Не нужны — локальные ACID |
| Скорость разработки | Медленнее | Выше |
| Масштабируемость | Высокая | Достаточная для учебного масштаба |

## 3. Диаграмма пакетов и список классов по пакетам

### Структура пакетов

Кодовая база разделена на 6 модульных пакетов с однонаправленными зависимостями (Directed Acyclic Graph):

| № | Пакет | Ключевые классы / контроллеры |
|---|---|---|
| 1 | **Presentation Layer** | `StudentPortalController`, `WardenDashboardController`, `AdminConsoleController` |
| 2 | **Identity & Access** | Домен пользователей, ролевая модель RBAC, модуль защиты ПДн (152-ФЗ) |
| 3 | **Dormitory Inventory** | Учёт корпусов, комнат, койко-мест; `AutoSearchEngine` |
| 4 | **Tenancy Core** | Заявления, договоры найма, заселение и выселение жильцов |
| 5 | **Maintenance & Repairs** | Заявки на ремонт, диспетчеризация, журнал дефектов |
| 6 | **Billing & Analytics** | Начисления, реестр задолженностей, аналитические отчёты |
| — | **External Gateways** *(external)* | Адаптеры банковского шлюза (СБП/эквайринг), шлюза уведомлений (SMS/Email) |

### Анализ зависимостей

- `Presentation` зависит от доменных пакетов; доменные пакеты ничего не знают о слое представления.
- `Tenancy Core` зависит от `Dormitory Inventory` (статусы мест) и `Identity & Access` (привязка студента).
- `Billing & Analytics` зависит от `Tenancy Core` (параметры договора) и `External Gateways`.
- Циклические зависимости **полностью отсутствуют**.

## 4. Диаграмма компонентов и таблица «компонент — ответственный — хранилище»

| Компонент | Назначение | Ответственный | Хранилище данных |
|---|---|---|---|
| **Web UI & REST Controllers** | Пользовательский интерфейс жильцов и персонала, обработка HTTP-запросов | Разработчик 1, 2, 3 | Stateless (сессии в защищённых JWT) |
| **Security & Identity** | Аутентификация, авторизация по ролям (RBAC), шифрование ПДн | Разработчик 3 | PostgreSQL (схема `auth`) |
| **Auto-Search Engine** | Алгоритмический подбор свободных мест по критериям | Разработчик 2 | In-memory кэш + PostgreSQL (`rooms`) |
| **Tenancy & Check-In Core** | Заявления, бронирование, договоры найма, заселение, выселение | Разработчик 1 | PostgreSQL (`tenancy`) |
| **Maintenance Module** | Заявки на ремонт, диспетчеризация, журнал устранения неисправностей | Разработчик 2 | PostgreSQL (`maintenance`) |
| **Billing & Debt Module** | Начисления, задолженности, интеграция с платёжным шлюзом, отчёты | Разработчик 3 | PostgreSQL (`billing`) |

**Решение:** система остаётся единым развёртываемым компонентом (модульный монолит) с общей базой данных PostgreSQL, разделённой по схемам. Для учебного масштаба выделение отдельных сервисов не оправдано.

## 5. Диаграмма развёртывания и пояснение

### Узлы и физическая топология

| Узел | Описание |
|---|---|
| **Клиентское устройство** | ПК коменданта/администратора или смартфон студента; браузер (Chrome, Edge, Safari) |
| **Сервер приложений** (Linux Ubuntu 24.04 LTS) | Nginx (TLS 1.3, Gzip, WAF) + исполняемый артефакт `dormitory-app.jar` |
| **Сервер базы данных** (PostgreSQL 16) | Изолированная Private VLAN; прямой доступ из интернета закрыт; внутренний TLS |
| **Внешний платёжный шлюз** (Банк / СБП) | Взаимодействие по HTTPS mTLS REST API с взаимной валидацией сертификатов |

### Как развёртывание обеспечивает атрибуты качества

- **Защита ПДн (152-ФЗ):** физическая изоляция сервера БД в Private VLAN исключает прямой доступ из интернета; персональные данные зашифрованы на уровне полей БД (`pgcrypto`); администраторы получают доступ к серверу БД только через VPN образовательной организации.
- **Надёжность транзакций:** все операции заселения выполняются на уровне сервера приложений в рамках ACID-транзакций с блокировками PostgreSQL.

## 7. Таблица сценарного прохода и найденный пробел

**Ключевой сценарий:** «Оформление заселения с автоматическим подбором свободного места и подписанием договора»

| № | Шаг сценария | Пакет | Компонент | Узел | Что может пойти не так | Архитектурное решение |
|:---:|---|---|---|---|---|---|
| 1 | Студент подаёт заявку | `Presentation` | `Web UI Controller` | Клиент → Сервер приложений | Потеря запроса при сбое сети | Идемпотентность API по токену `idempotency_key` |
| 2 | Комендант запускает автоподбор | `Dormitory Inventory` | `Auto-Search Engine` | Сервер приложений | Два коменданта выбирают одно место | Алгоритм возвращает кандидатов; окончательный захват — только в транзакции |
| 3 | Подтверждение и бронирование | `Tenancy Core` | `Tenancy & Check-In Core` | Сервер → Сервер БД | **Гонка данных (Race Condition), овербукинг** | Пессимистическая блокировка: `SELECT ... FOR UPDATE` |
| 4 | Формирование договора найма | `Tenancy Core` | `Tenancy & Check-In Core` | Сервер приложений | Сбой генератора PDF | Метаданные договора — в транзакции с бронью; PDF генерируется асинхронно |
| 5 | Студент подписывает договор | `Presentation` → `Tenancy Core` | `Web UI → Tenancy Core` | Сервер приложений | Таймаут ожидания подписи | Резерв места 48 ч.; cron-задание освобождает место при неподписании |
| 6 | Активация статуса жильца и начисление | `Tenancy Core` → `Billing` | `Tenancy Core` → `Billing & Debt Module` | Сервер → Сервер БД | Заселение есть, счёт не создался | Доменное событие `StudentCheckedInEvent` + паттерн Transactional Outbox |

**Найденный пробел:** при сбое на шаге 6 (после успешного заселения) биллинг не получает уведомления и первый месяц проживания остаётся неначисленным. **Решение:** вызов модуля биллинга выполняется через доменное событие с гарантированной доставкой (Transactional Outbox).

## 8. Запись архитектурного решения (ADR-001)

**Решение:** «Модульный монолит» и пессимистическая блокировка для предотвращения овербукинга

**Контекст:** разрабатывается система управления общежитием. Ключевые требования — недопущение двойного заселения на одно койко-место, защита ПДн по 152-ФЗ, высокая скорость разработки командой из 3 человек за 4 месяца.

**Рассмотренные альтернативы:**
1. *Микросервисная архитектура* — высокая сложность, распределённые транзакции (Saga/2PC), избыточна для команды из 3 человек.
2. *Модульный монолит* (выбрано) — локальные ACID-транзакции, единая БД, быстрая разработка.

**Последствия:**
- ✅ Гарантированная транзакционная согласованность без сложности распределённых систем.
- ✅ Скорость разработки и отладки для малой команды.
- ⚠️ Горизонтальное масштабирование ограничено — для учебного масштаба несущественно.

- Оформление **архитектурного решения ADR-001** по шаблону.

**Ответы на контрольные вопросы:**

**1. Почему выбран модульный монолит, а не микросервисы?**  
Для команды из 3 человек и срока 4 месяца микросервисная архитектура создаёт непропорционально высокие накладные расходы на оркестрацию, мониторинг и распределённые транзакции. Модульный монолит обеспечивает те же атрибуты качества при значительно меньшей сложности.

**2. Как предотвращается овербукинг?**  
Захват койко-места выполняется строго в ACID-транзакции с пессимистической блокировкой (`SELECT ... FOR UPDATE`). Второй параллельный запрос ожидает снятия блокировки и получает статус «Место уже занято».

**3. Как обеспечивается защита персональных данных?**  
Трёхуровневая защита: шифрование полей БД (`pgcrypto`), ролевая модель RBAC, физическая изоляция сервера БД в Private VLAN с закрытым прямым доступом из интернета.
