# Атрибуты качества и выбор архитектурного стиля

## 1. Измеримые атрибуты качества

| Атрибут качества | Неизмеримая (плохая) формулировка | Измеримая формулировка для системы управления общежитием |
|---|---|---|
| **Защита персональных данных (ПДн)** | «Система должна надёжно защищать данные студентов» | Паспортные данные, контактные телефоны и адреса жильцов хранятся в зашифрованном виде (AES-256) в изолированном контуре БД. Доступ строго ограничен ролевой моделью (RBAC): комендант видит жильцов только своего корпуса, студент — только свой профиль. В открытые системные логи персональные данные не попадают (маскирование). |
| **Надёжность и транзакционность распределения мест** | «Система не должна давать сбоев при заселении» | Процедура распределения места и заключения договора найма выполняется в рамках атомарной ACID-транзакции с пессимистической блокировкой койко-места (`SELECT ... FOR UPDATE`). Ситуация овербукинга (одновременное заселение двух студентов на одно место) исключена на 100% даже при параллельных запросах комендантов. |
| **Производительность автоматического поиска мест** | «Поиск комнат должен работать быстро» | Время выполнения алгоритма автоматического подбора свободных мест с фильтрацией по полу, курсу, факультету и корпусу составляет **не более 1.0 секунды** при базе в 5 000 студентов и 2 000 койко-мест при одновременной нагрузке до 50 запросов в секунду. |
| **Сопровождаемость и расширяемость** | «Систему должно быть легко обновлять» | Добавление нового тарифа оплаты, типа комнаты или статуса заявки не требует модификации программного кода — выполняется через справочники и миграции схемы данных. |

## 2. Ограничения проекта
- **Размер команды:** 3 человека (Тимлид/Бэкенд, Фулстек/Алгоритмы, Фулстек/Финтех и безопасность).
- **Срок разработки:** 1 семестр (4 календарных месяца).
- **Суммарный трудовой ресурс:** 12 человеко-месяцев.
- **Инфраструктурные ограничения:** Единый виртуальный выделенный сервер (VPS) образовательной организации.

## 3. Выбор архитектурного стиля
Для системы выбран стиль **«Модульный монолит» (Modular Monolith)**. 
*Обоснование:*
1. Архитектура микросервисов для команды из 3 человек и срока в 4 месяца категорически не подходит из-за колоссальных накладных расходов на оркестрацию, сетевые вызовы, распределённые транзакции (Saga) и сетевую инфраструктуру.
2. Простой монолит без строгого разделения на слои чреват превращением кодовой базы в «спагетти» и утечкой доменных границ.
3. Модульный монолит обеспечивает строгую изоляцию бизнес-модулей (Identity, Inventory, Tenancy Core, Maintenance, Billing) через контракты интерфейсов внутри единого процесса приложения, использует общую реляционную БД с логическим разделением схем и позволяет при необходимости в будущем безболезненно вынести высоконагруженный модуль в отдельный микросервис.
